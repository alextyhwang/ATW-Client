I recompiled the frozen trajectory/command test sources into the private directory and executed them against the frozen candidate jar, Java 17, cached Weave 1.4.1 dependencies, and the mapped 1.8.9 game jar. No Gradle build or shared module output was changed. **24 tests passed, zero failures/skips/aborts:** 18 existing trajectory/lifecycle/command tests plus six private review tests. The rerun reproduced **843 parity comparisons (522 full paths, 321 targeted collision cases) and 1,966 parity-harness assertions**; that assertion count excludes JUnit lifecycle/private assertions. Both former negative controls, the stateful bounding-box getter and second block trace visibility mutation, pass, as does first-trace ordering. The retained canonical XML independently totals 42 tests with zero failures/errors/skips; this review reran the 18 relevant tests rather than the unrelated 24 minimap helper tests. [offline-tests.log](../upgrade-work/pvp-experiments-20261006/trajectory-review-1/offline-tests.log) and the private runner/test sources retain the execution evidence.

The six additional regressions cover: actual strong-reference cleanup and recovery after a getter exception; actual cleanup on normal return; unknown collection iteration without custom `size()`; getter-time position mutations before interpolation; signed-zero and same-identity bound changes; and nearest-tie identity when reordered players share all metadata and the original box.

At 32 stable targets over 160 segments, the existing lifecycle test independently verifies 5,120 live bounding-box reads and 5,120 UUID network lookups in both arms. OFF records 5,120 original offset/expand preparations; ON records 32 preparations and 5,088 reuses. The parity harness's printed `offsets=0`/`expands=0` for exact vanilla boxes is a fixture instrumentation limitation: those method counters instrument subclasses only. The allocation-pair counts come from candidate counters and the reviewed call sites, not those zeros and not an allocation profiler.

OFF preserves original simulation/getter/collision/drawing behavior, but **OFF is not a zero-overhead implementation**. It still increments saturated render/compute counters, tracks wrapper/reentry state, increments the iterator ordinal, and increments `baselinePreparations` once per eligible player/segment, including 5,120 increments in the workload above. Scratch arrays and client-thread/list-size admission checks are bypassed while OFF; no timer, extra classifier or network query is added. The cost of these branches/writes was not measured. ON allocates a fresh bounded scratch with nine 256-element double arrays and three reference arrays per admitted compute; small/ineligible scenes may not benefit. Neither arm has measured game performance evidence.

**Approval limits:** exact AABB class checks do not prove purity, immutability under transformation, or equivalent effects of Lunar-composed `offset`, `expand`, and collision methods. Reuse skips repeated preparation calls and retains a derived instance within a computation; transformations could make either distinction observable. The implementation/documents honestly expose `liveQualified=false` and startup OFF. World guards operate at segment-scan boundaries; this screen does not establish arbitrary concurrent mutation safety. Unsafe fixtures, synthetic block traces, and an altered owner-thread field are source parity/fallback tests, not live chunk traversal, transformed-class admission, real worker-thread concurrency, physical input, or combat/GL qualification. Approval must not be presented as proof of those properties. Parent runtime review must establish the actual composition and active-item behavior before claiming live qualification or measured benefit.
