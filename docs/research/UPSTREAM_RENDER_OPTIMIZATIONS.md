# Upstream mechanisms for ATW Render Boost

Research only, 2026-10-05; branch `performance/weave-1.4.1-mc1.8.9`. **Recommendation:** first investigate remaining client render allocations and the existing Lunar terrain batching path; consider build scheduling if moving-scene traces show chunk-build/upload stalls. A Sodium-style renderer replacement has a larger possible scope but substantially worse compatibility. All benefit estimates below are hypotheses, not FPS predictions. No implementation, build, installation, game launch or benchmark was performed for this note.

## Repository facts and constraints

- [AGENTS.md](../../AGENTS.md), [MODS.md](../../MODS.md) and [Render Boost's build configuration](../../weave-mods/atw-render-boost/build.gradle.kts) fix Minecraft **1.8.9**, Weave **1.4.1**, Java **17** toolchain and Java **8** mod bytecode. Upstream modern mod jars are not compatible substitutes.
- [NAME_PARSE_PERFORMANCE.md](../NAME_PARSE_PERFORMANCE.md) records **473.064 → 532.491 average FPS**, a **12.562% observed increase**, across eight short moving Bedwars Practice trials. Scene populations varied; this is neither a Hypixel result nor proof of a universal gain. Hypixel connectivity remains unresolved. Name caching was active; terrain, glyph and error-poll experiments were OFF.
- [NameParseCache.java](../../weave-mods/atw-render-boost/src/main/java/com/atw/renderboost/cache/NameParseCache.java) retains immutable decoded strings in a bounded LRU. [NameParseRuntime.java](../../weave-mods/atw-render-boost/src/main/java/com/atw/renderboost/cache/NameParseRuntime.java) still creates fresh native compounds/string tags on hits. The [exact hook targets](../../weave-mods/atw-render-boost/src/main/java/com/atw/renderboost/hook/NameParseHook.java) include NBT constructors/classes: changing their implementations can invalidate the measured optimization's evidence.
- [Render Boost's README](../../weave-mods/atw-render-boost/README.md) reports that Lunar already caches/batches text. Its terrain VAO experiment preserves every draw and only caches pointer setup; it requires the captured **28-byte BLOCK** format, Regions/shaders OFF and an inactive opaque modelview callback. It is not a batching implementation. [TerrainEligibility.java](../../weave-mods/atw-render-boost/src/main/java/com/atw/renderboost/terrain/TerrainEligibility.java) explicitly rejects Regions, custom programs and foreign VAOs.
- [ENVIRONMENT_RECOVERY.md](../ENVIRONMENT_RECOVERY.md) records execution of Lunar/OptiFine `VboRegion.finishDraw` / `VboRenderList.drawRegion` native multi-draw with Render Regions ON, but no qualified ON/OFF benefit. Sample counts do not establish time fractions. Driver VSync recovery is separate from mod gains.
- [Overlay guidance](../../weave-mods/optimal-zone/AGENTS.md) and [README](../../weave-mods/optimal-zone/README.md) require normal visible-player rendering and one full normal player pass. Terrain visibility must not suppress the hidden-player/invisibility overlays, duplicate armor/held-item rendering, or turn chams into box ESP. LevelHead remains the sole packet-to-chat bridge.

### Sodium: transferable ideas, with their boundaries

1. **Batch compatible terrain submissions.** [DefaultChunkRenderer][S-draw] builds reusable multi-draw command arrays per region/render pass, uses region geometry buffers and cached tessellations, and distinguishes shared opaque indices from translucent indices. It masks empty and camera-invisible directional mesh slices. **Transfer inference:** fewer Java/native submissions and repeated state setups may help a CPU submission bottleneck. First evaluate Lunar's existing Regions path; stacking another renderer onto it could duplicate work or corrupt state. Preserve layer order and translucent sorting.
2. **Traverse section visibility with compact state.** [OcclusionCuller][S-cull] uses reusable queues, frame visitation markers, incoming/outgoing direction masks and precomputed section connections, plus frustum/distance tests. It includes expanded bounds and nearby-section handling for models outside nominal section bounds. **Transfer inference:** compact traversal bookkeeping could reduce CPU allocation/work while preserving the existing visible set. Do not equate this with GPU occlusion queries or entity culling; modern fog/bounds assumptions require separate 1.8.9 proof.
3. **Build meshes from snapshots with reusable worker contexts.** [LevelSlice][S-slice] copies block/light/biome data for consistent off-thread access and bypasses empty sections. [ChunkBuilderMeshingTask][S-mesh] visits blocks, renders model/fluid geometry, computes section occlusion, checks cancellation and hands results to main-thread upload. [ChunkBuilder][S-builder] owns a context per worker. **Transfer inference:** bounded snapshots and worker-local scratch can reduce repeated lookups/allocation and synchronization. Establish what Lunar already does before adding another pool; live world reads from new worker threads are not safe merely because rendering is read-only.
4. **Budget and prioritize build work.** [ChunkBuilder][S-builder] uses queued effort and worker count to distinguish heavier meshing from lighter sorting. [RenderSectionManager][S-manager] separates important/deferred work, can wait for important tasks, and filters disposed, stale and duplicate results before upload. **Transfer inference:** coalescing obsolete rebuilds and bounding work may improve moving-scene tails. This source does **not** establish a universal millisecond upload budget; a separate byte/time upload limit would be an ATW design choice. Never defer nearby block changes until players see stale geometry.
5. **Bound pure-result caches and pack hot data.** [BlockOcclusionCache][S-face] uses a 512-entry shape-comparison LRU, a reusable lookup key and mutable position scratch. Special block behavior is checked before cache lookup. [CompactChunkVertex][S-vertex] packs a vertex into **20 bytes**, with matching shader decoding; [ChunkMeshBufferBuilder][S-buffer] writes contiguous native buffers. **Transfer inference:** retain the cache discipline and dense bookkeeping, not the modern shape API or vertex bytes. A state-ID-only 1.8.9 face cache is insufficient when neighbors, position, lighting or resource models affect results. The 20-byte format cannot replace ATW's captured 28-byte format without changing producer, shader/consumer and hook evidence together.

### Lithium: allocations and world queries, not a terrain renderer

- [Enum allocation documentation][L-enum] avoids repeated defensive `values()` array copies using an internal stored array. **Transfer inference:** apply only to proven hot client callsites whose consumers cannot mutate/retain the shared array. The [living-entity example][L-enum-example] concerns equipment-change detection; it is evidence of the technique, not proof of a Lunar frame hotspot.
- [NbtCompoundMixin][L-nbt] replaces standard HashMap storage with open-addressed fastutil maps and preserves deep copying. **Transfer inference:** contiguous lookup/storage can reduce object overhead, but a global NBT rewrite is a poor next experiment here: it touches broad semantics and exact name-cache gates. Do not pool or share the fresh mutable NBT/component results required by ATW's current cache.
- [ChunkAwareBlockCollisionSweeper][L-sweep] skips empty sections, caches section access, uses mutable position scratch and walks storage in a largely linear order. [WorldHelper][L-query] restricts collision searches to applicable class groups with vanilla fallback and handles both client/server entity caches. [Movement mixin][L-movement] delays entity queries and preserves sensitive collision ordering. **Transfer inference:** storage-local scans and query narrowing are reusable ideas; movement replacement is a separate gameplay-sensitive project, not a render optimization.

## Inapplicable or deferred

**Execution side matters.** Sodium affects the local client renderer. Lithium can affect client logic and a local integrated server, or dedicated-server logic when installed there; its [configuration descriptions][L-config] include AI/pathfinding, hopper sleeping, block-entity ticking and chunk ticking. Improving an integrated server can reduce single-player CPU contention, but does not optimize the remote Hypixel server. A client installation cannot reduce Hypixel's server AI, redstone, hopper or world-generation work. Client collision/entity-query work is a distinct, conditional opportunity.

Modern POIs/Brain sensors, waterlogging, voxel-shape implementations and modern sectioned entity storage are not direct 1.8.9 ports. Modern loader mixins, LWJGL native-memory helpers and shader formats also require new integration rather than copied hook names. No upstream evidence justifies reducing render distance/quality, suppressing names/players, adding synchronous occlusion-query readbacks, greedy-merging arbitrary textured/AO/translucent quads, or enabling ATW's failed glyph/error-poll/terrain experiments.

## Proposed validation sequence — not executed

1. Freeze the current successful name-cache baseline and settings; keep other experiments OFF. Attribute remaining client CPU, allocation, terrain submission and build/upload cost separately. Inclusive nested name timings are not additive; GPU waits can appear inside unrelated GL calls ([existing diagnostic cautions](../../weave-mods/atw-render-boost/README.md)).
2. Select one candidate only when its hotspot is material. Require unknown-runtime fallback and lifecycle/thread/resource guards comparable to Render Boost's existing gates. Validate visual/state/exception parity before interpreting performance.
3. Later compare isolated OFF→ON→ON→OFF moving trials with longer warmup/windows, repeat blocks, fixed drawable/quality/camera route, actual activation counters and allocation/queue metrics. Report median/p95/p99 intervals as well as throughput; validate instrument overhead in separate controls.
4. Bedwars Practice remains fallback evidence. Hypixel crowd/movement acceptance and feature parity stay outstanding until connectivity is resolved. Single-player/integrated-server improvements cannot substitute for that result. No candidate supports a doubled-FPS claim.
