# Multiplayer client performance: upstream mechanisms and port boundaries

Research only, **2026-10-06**. Scope: the **local Lunar 1.8.9 client playing on remote servers**, especially stationary play at **12–16 chunks**, many nearby players, responsive interactions, and fewer hitches. No remote-server modification, implementation, build, installation, game launch, attachment, profiling, benchmark, or settings change was performed. Only this document was written. Network latency is the parent's separate research track; local code attribution belongs to the other worker.

**Recommendation:** investigate player/armor/item submission, remaining HUD/name preparation, client chunk-update tails, and particle CPU work, in that order for the stated workload. These are conditional research priorities, not promised gains or instructions to enable experimental switches. A stationary crowd and a chunk-arrival burst need different measurements.

## 1. Players, armor and held items: compact work versus existing lists

### What the code establishes

**Stock:** `ModelRenderer.render` (`bct.a(F)V`, SRG `func_78785_a`) checks the compiled flag, invokes `compileDisplayList` (`bct.d(F)V`, `func_78788_d`) when needed, applies per-part transforms, and calls `GlStateManager.callList`; `bfl.o(I)V` directly invokes `GL11.glCallList`. Compilation opens `GL_COMPILE`, traverses `ModelBox` geometry, ends the list and sets the flag. The part mesh is therefore not rebuilt in Java on every ordinary frame. [Official artifact and naming provenance][MC-meta] [MCP mappings][MC-mappings] [Forge compilation context][F-model]

**Upstream:** Patcher's [ModelRenderer mixin][P-model] starts one `WorldRenderer` batch **inside `compileDisplayList`**, draws it before `glEndList`, and invalidates compilation when the batching option changes. Its [TexturedQuad mixin][P-quad] suppresses face-local begin/draw when an enclosing batch is active, retaining standalone fallback. PolyPatcher's [model][PP-model] and [quad][PP-quad] files retain this mechanism.

**Interpretation:** this can change the **recorded command stream**, potentially replaying fewer face draw commands on later frames, as well as reducing compilation work. It does **not** merge separate animated body parts or multiple players into one per-frame draw. Display lists already remove repeated Java face tessellation; fewer commands inside a list and fewer Java `glCallList`/matrix/state calls are distinct opportunities. Neither gain is established on Lunar. Counting only warmup tessellator calls would miss recorded commands; counting only Java list calls would miss internal replay work.

**Stock armor:** the inspected texture-resource lookup (`bkn.a(Lyj;ZLjava/lang/String;)Ljy;`) formats a texture key and uses a static map to reuse `ResourceLocation`s; formatting/allocation still occurs before lookup. Forge's [armor patch][F-armor] shows model attribute/animation setup, dyed texture/overlay passes, enchant passes and texture caching, plus item-sensitive Forge hooks. These are layer/lookup seams, not evidence that armor geometry must be regenerated. Lunar-specific dynamic resources/cosmetics may invalidate simple finite-key assumptions.

**Upstream item option:** PolyPatcher's [ItemLayerModel change][PP-item] scans sprite frames/alpha, records side faces and builds fewer side quads, with distinct translucent handling. It targets **Forge's bake-time `ItemLayerModel`**, not the normal animated player mesh. Fewer baked quads could reduce repeated item submission, but no corresponding Lunar target or pixel parity is established. It can affect texture edges, holes, animated frames and lighting; defer rather than label it a safe generic item optimization.

### Proposed narrow work and larger work

1. **First establish the executed path.** Separate one-time model compilation, pose calculations, armor selection, texture-key construction, baked-item quad submission, GL transitions and Overlay base passes. Distinguish loaded from actually rendered players and normal model parts from cosmetics. If Lunar already compiles a single batch per part, Patcher's change has nothing additional to save there.
2. **Compact preparation is the nearer hypothesis.** Reuse private scratch/finite immutable lookup results and dense per-player pass descriptors at measured hot sites. A finite armor resource lookup could avoid repeated formatting only when dynamic resource selection is proved absent or included in its key. Keep mutable model/ItemStack/component state private to its owner; never share a cached pose between differently posed players or omit required callbacks. Existing state caches may already suppress redundant binds.
3. **Per-player compact submission is a larger hypothesis.** Shared static cuboid geometry plus per-part transforms, or a complete posed-player vertex batch for one compatible material/pass, could reduce repeated matrix/list calls. CPU-transforming all vertices each frame can lose to cached lists; a shader/instancing design requires new LWJGL 2 capability, vertex format, normal/lighting and OptiFine/Lunar integration. These are alternatives to evaluate, not interchangeable “batching” toggles.
4. **Crowd-wide batching is more constrained.** Players usually have different skin textures and poses. Armor may share materials but has dye/glint and depth/order requirements; held items have independent transforms/materials. A texture-only batch key is insufficient. At minimum include material/texture, geometry/format, lighting, transform ownership, blend/alpha/depth, cull state, shader, and stencil/polygon-offset **pass identity**. Unknown cosmetics/custom models fall back. Do not reorder across a player's stencil capture, normal pass and overlay application; full crowd grouping may be incompatible with the present Overlay sequence.

ImmediatelyFast's [buffer source][IF-batch] groups buffers by modern render layer, tracks pending layers, controls flushing/order and has explicit special ordering for transparency/text. Its [HUD buffer][IF-hud] additionally distinguishes item lighting state, and its [state record][IF-state] preserves shader/textures/color/blend/depth. **Transferable concept:** batch only compatible work, preserve required boundaries, reuse owned buffers. This is not proof that a 1.8.9 fixed-function player renderer can use its implementation, nor a basis for importing its published FPS comparisons.

**Promotion proof:** fewer effective commands/preparation bytes at equal rendered-player, part and layer counts; reduced relevant CPU/GPU time and stable frame tails. Validate Steve/Alex, all armor slots, dyed/enchant armor, skins/hat layers, held/swinging/using items, sneaking/riding/hurt/death/invisibility, cosmetics, resource reloads, perspective changes and both chams/invis paths. Compilation cold starts and steady replay require separate windows.

## 2. Scoreboard, tab, nametags and text

**Stock bytecode:** `GuiIngame.renderScoreboard` (`avo.a(Lauk;Lavr;)V`, `func_180475_a`) obtains sorted scores, filters/copies rows, formats team names and score strings, and measures widths before drawing. `GuiPlayerTabOverlay.renderPlayerlist` (`awh.a(ILauo;Lauk;)V`, `func_175249_a`) uses Guava `Ordering.sortedCopy`, formats/measures names, wraps header/footer text, and draws heads, scores and ping indicators. This establishes preparation work in stock 1.8.9, **not that current Lunar repeats it**. [Mojang bytes][MC-jar] [Mapping provenance][MC-mappings]

Patcher's [entity cache][P-name] returns the **same mutable chat component** for up to 50 ms; its [player cache][P-player-name] applies that cache and avoids hover construction outside integrated-server mode. This is broader and semantically different from ATW's immutable parse cache with fresh native results. Do not copy the TTL/aliasing policy or revive the low-gain forward/reverse experiments under a new name. Server team/score/name changes, Lunar formatters and hover/click callbacks must remain observable.

**Proposal:** retain immutable prepared rows/name text/widths and stable tab ordering between actual changes. Invalidate on objective/display-slot/score/team changes, player-info add/remove/name/game-mode changes, formatter/LevelHead changes, resource/font/language/GUI-scale changes, world/reconnect changes and relevant local setters. Ping/health animation remains live or separately keyed; tab is only a workload while displayed. Derive visibility/team rules from current state, rather than storing their decisions indefinitely. Preserve new mutable outward objects wherever callers may alter them. If reliable invalidation cannot be proved, reject the candidate instead of adding a long refresh interval.

**Already covered:** Lunar text batching/list caching and ATW name parsing are repository records. Determine their hit/miss/cost boundaries before building another cache. The proposed value is in residual sorting, layout/formatting and allocations, not necessarily glyph geometry. Existing name-cache hook admission can be broken by broad NBT/component rewrites.

**Deferred upstream approach:** Patcher/PolyPatcher [HUDCaching][PP-hud] replays a framebuffer until a refresh/dirty condition and selectively renders captured elements outside it. This can reduce draw work but changes update cadence and needs special handling for crosshair blending/animations. Whole-HUD caching is a poor default for responsive combat, LevelHead and Overlay's per-frame minimap. Prefer exact dirty data preparation, while drawing current dynamic elements each frame. Nametags also move with camera/player interpolation and cannot simply reuse yesterday's screen-space image.

**Proof:** residual CPU/allocation reduction with cache hits and explicit invalidation counters; names, prefixes/suffixes, ordering, scores, ping/health animation, header/footer, Unicode and hover/click parity during rapid updates. No frame of stale team membership or delayed interactive feedback. Instrument nested parse/layout/draw timing without adding overlapping durations together.

## 3. Receiving chunks: client work after a remote server sends data

**Stock inspected flow:**

1. `NetHandlerPlayClient.handleChunkData` (`bcy.a(Lgo;)V`, `func_147263_a`) and `handleMapChunkBulk` (`bcy.a(Lgp;)V`, `func_147269_a`) invoke `PacketThreadUtil.checkThreadAndEnqueue` before world updates. `fh.a(Lff;Lep;Lod;)V` schedules the packet on the thread listener when necessary. Asynchronous network IO is not asynchronous world mutation. [Official bytecode][MC-jar] [Mappings][MC-mappings]
2. Handlers load/unload client chunks as specified, invalidate affected regions, call `Chunk.fillChunk`, mark rendering updates, and conditionally reset relight work. Bulk handling performs the operations across received chunks. `Chunk.fillChunk` (`amy.a([BIZ)V`, `func_177439_a`) decodes section block-state data, copies block/skylight/biome arrays, refreshes section counts and heightmap state, and updates tile-entity information. [Official bytecode][MC-jar] [First-party fill context][F-chunk]
3. Meshing, queueing, GPU upload and later region draws are subsequent stages. Existing Lunar/OptiFine worker/snapshot/queue behavior must be established independently; [prior source research](UPSTREAM_RENDER_OPTIMIZATIONS.md) already covers snapshot-local reads, stale rebuild cancellation and worker scratch as conditional concepts.

**Why stationary play still matters:** no camera translation can make terrain builds quiet, but server block changes, arriving/replaced chunks, entity/tile updates or world transitions can still create bursts. More configured view distance is not proof of a higher incoming-chunk rate or of expensive remote generation. Record actual client-loaded sections, arrivals and dirtiness. A stationary crowd normally favors player/HUD work; teleport/join tails may favor this track.

**Patcher/PolyPatcher mechanisms and exclusions:**

- [ChunkHook][P-chunk-hook] makes bounded direct section/storage access and returns air for out-of-height/empty storage; [its mixin][P-chunk] also modifies a relight Y argument. Direct lookup is useful only where residual repeated access is measured; it is not a fast replacement for decoding an entire packet. Do not import the relight change as an unexplained speed trick.
- PolyPatcher's [chunk unload hook][PP-unload-chunk] and [world removal hook][PP-unload-world] accumulate unloaded chunk keys, then remove matching tile entities from lists in passes. **Proposal:** batch repeated bookkeeping when client unload churn is actually material. Require unload/reload identity, invalidation and callback parity, particularly if the same chunk coordinate returns before processing.
- PolyPatcher's [early-light fix][PP-light] adjusts area/range conditions; it is a lighting correctness change with possible work implications, not evidence that disabling light work is safe. Fullbright/light suppression is excluded.
- Patcher's [chunk update limit][P-limit] sleeps 50 ms while a global update-count limit is reached. It does not establish a good millisecond frame budget. Do not copy the sleep loop: artificially slow terrain completion may improve an FPS counter while delaying fresh blocks.
- Anvil save/load, disk-region IO, world generation, server lighting, server entity tracking and integrated-server optimization are outside this remote-client task unless a separately measured local client path actually executes them.

**Proposal:** first remove unnecessary copies/allocation and stale **render rebuilds**, preserving ordered application of all server data. Later, bounded snapshot/worker scratch and upload scheduling could reduce competition with interactive frames. Budgeting may introduce visible update lag or starvation; measure queue age and chunk/block readiness, not only frame time. Never move live `WorldClient` mutation to Netty workers, reorder gameplay packets, drop server changes, or coalesce ordered packet semantics merely because final meshes can be coalesced.

## 4. Particles: retain effects and distinguish ticking from submission

**Stock:** `EffectRenderer.renderParticles` (`bec.a(Lpk;F)V`, `func_78874_a`) loops layer/alpha lists, begins a shared `WorldRenderer` batch, calls individual particle vertex emission and draws after each bucket. Ordinary particles therefore already have coarse batching. Special/lit/custom paths need separate inspection; do not presume one draw per particle. [Mojang bytecode][MC-jar] [Mappings][MC-mappings]

Patcher's [particle mixin][P-particle] records a frustum result after **ticking** and tests it before `renderParticle`; [helper][P-particle-helper] defaults to drawing without a camera. The optimization saves some render preparation for offscreen particles; it does **not** skip the particle tick in this implementation. A tick-sampled camera/bounds result can be stale during a rapid turn or miss a large billboard extending beyond an entity box. A direct copy has no exact visibility guarantee.

**Proposal:** first find allocation, collision/update, camera-vector, color/light or vertex-writing costs at actual hot client sites. Reuse private render scratch and preserve the existing layer/alpha batches and visible particle order. A conservative current-frame frustum decision is conditional on an expanded bound that contains the entire rendered effect through interpolation; unsupported classes/renderers, moving cameras and uncertain bounds retain original rendering. It must not reduce spawn counts, lifetimes, ticking, effect frequency, depth/alpha appearance or combat cues.

ImmediatelyFast supplies buffer-ownership/batching concepts, but its modern particle claim is not proof of a useful legacy seam. Offscreen vertex savings can be small when existing batches are already efficient; dense visible alpha effects can remain GPU/fill limited. Fewer draws alone cannot repair overdraw, and dropping effects is outside scope.

## Later benchmark and acceptance evidence — none executed here

**Baseline/control:** freeze exact executable/loader/API/Lunar/mod hashes, effective name-cache/Regions states, disabled experiments, resource pack, drawable, cap/VSync/focus, distance (separate 12 and 16), quality, FOV and GUI scale. Keep baseline caches ON in every candidate OFF/ON comparison. No builds, source fetches, other workers, profiling or high-volume diagnostics during measurement. Use separate low-overhead counters and profiling attribution windows, with an instrumentation-only control.

**Representative workloads:** stationary visible crowd with moving/swinging/equipping players; stationary camera looking away from the same crowd as a diagnostic control; tab closed/open plus changing team/score/header data; particle-heavy fights with fast camera turns; joins/teleports/chunk bursts and nearby block changes; quiet baseline. Record loaded, visible and actually rendered players, armor/item/glint layers, NPCs, particles and chunk/packet rate. Remote scenes drift, so bracket candidate ON with returning OFF, repeat balanced blocks, warm routes/resources separately and publish population/churn distributions. Controlled offline visual scenes can establish parity, but cannot establish remote-server responsiveness or crowd benefit.

**Metrics and proofs:**

- **Frames:** frame interval median/p95/p99/p99.9 where sample size permits, throughput as frames divided by elapsed time, worst intervals, and stall counts **per second/minute** above predeclared thresholds (e.g. 5/10/16.7/50 ms). Retain all intervals; explain warmup exclusions in advance. CPU wall frame timing includes limiter/presentation; separate render CPU, GPU and waits where tooling permits. Improving average FPS or frame-fraction tails alone does not prove fewer hitches.
- **Players:** normal pass/overlay pass CPU, pose/setup/armor/item/text time and allocated bytes per rendered player; compilation count/time, parts/list calls, effective recorded draws and material/state changes. Do not add inclusive nested timings. Match output counts and verify screenshots/video/pose matrices and GL state restoration before interpreting speed.
- **HUD:** layout/sort/format/width cost, immutable cache hits/misses/size, invalidations and update-to-display delay. Verify no stale names, teams, scores, colors, tab ordering or delayed minimap/LevelHead. Activation requires requested **and admitted and actually executed** evidence, not class installation alone.
- **Chunk pipeline:** arrival bytes/count, decode CPU/allocation, Netty-to-main queue delay, handler/fill/heightmap/light cost, stale mesh work/cancellation, build/upload time and bytes, backlog/oldest age, unload cost, GC/safepoints and server-change-to-client-visible delay. Synchronize stage timestamps locally; do not equate them to WAN RTT or remote server tick time.
- **Interaction:** timestamp local input sampling, client tick action, send enqueue/write and first corresponding local feedback where authorized tooling permits. Preserve packet ordering/flush semantics. Distinguish local delay from server confirmation and network/server variance; parent latency work supplies that attribution. FPS is not an input-latency measurement.
- **Promotion:** demonstrate repeated improvement beyond measured OFF/OFF and returning-OFF drift, with no tail/update-delay/visual regression in relevant scenes. Source tests and higher hit counts are necessary diagnostic evidence, not speed qualification. Unknown runtime, resource, world/thread/context lifecycle or cleanup failure must retain the original path and disable that experiment.

## Major limitations and handoff

No fresh Lunar bytecode admission, hotspot attribution, runtime counters or measurement was collected. Stock and modern upstream evidence explain mechanisms; they cannot show that Lunar lacks them, that they are active, or that a port is worthwhile after name caching and Regions. Model display lists, baked models, texture caches, stock particle batches and Lunar text/terrain batching substantially reduce the obvious opportunities. Unique player materials and Overlay's pass order constrain crowd batching. Occlusion cannot make a visible crowd cheaper, and player occlusion cancellation conflicts with the required hidden-player output. Packet decoding, world application and mesh work require separate attribution; remote-server optimizations do not run in this client.
