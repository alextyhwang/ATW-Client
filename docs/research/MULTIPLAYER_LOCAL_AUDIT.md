# Multiplayer local optimization audit

2026-10-06. Research only, against canonical working-tree source at HEAD `0ac5f2d` (with pre-existing uncommitted changes). Line anchors describe this audit-time source, not a verified loaded-class image.

**Recommendation:** measure the current crowded stationary multiplayer scene first, separating normal names, LevelHead, Overlay player passes, HUD markers and client ticks. The best locally grounded leads are repeated player-render state/metadata work, LevelHead render-side display-name work, and minimap scan/churn bookkeeping. A separate stationary chunk-arrival window should test minimap sampling/upload tails and the main-thread handoff. These are ranked investigation candidates, not established bottlenecks, safe patches or FPS forecasts.

Keep the accepted baseline: original names parse cache **ON**, OptiFine Render Regions **ON**, reverse encoding and forward hover **OFF**, and the other ATW renderer experiments OFF. Prioritize many loaded/rendered players while the camera is stationary, then chunk-arrival bursts. Terrain traversal is supporting historical evidence, not this plan's priority.

[PlayerMinimapRenderer.onTick:255](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L255) maintains world/yaw state and clears/reset snapshots/terrain on absent or changed world. 1. [Loaded-player census:1135](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L1135) scans `playerEntities` every tick for diagnostics.

[Adaptive zoom:529](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L529) checks every five ticks; [nearby counts:562](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L562) separately scans/classifies players and resolves teams, with an early exit at the crowded threshold.
3. [Marker snapshots:649](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L649) scan players every tick, classify again, radius-filter, then fetch color/invisibility/skin ID. [Skin lookup:884](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L884) repeats network-info lookup already performed by the classifier. It calls `getLocationSkin`, texture-manager lookup and `getGlTextureId`; no direct HTTP or filesystem read exists in this method. Underlying lazy skin loading is unresolved, so neither “blocking skin download” nor “free cached getter” is established.
4. [Fireball snapshots:697](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L697) scan the entire `loadedEntityList` each enabled tick, even when there are no fireballs. A separate active BedWars alert scan runs every five ticks ([BedwarsBaseAlertManager.java:134](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/BedwarsBaseAlertManager.java#L134), [158](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/BedwarsBaseAlertManager.java#L158)). These scans have different radius/filter semantics and cannot simply share the currently displayed subset.

HUD [render:333](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L333) interpolates numeric snapshots and draws them; it does not rescan world players, resolve teams or fetch skins. [Snapshot pools:1223](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L1223) reuse marker/fireball objects and grow arrays only when needed. Color/skin/invisibility are refreshed on ticks, not a long-lived metadata cache with change-event invalidation. There is a per-HUD-render `ScaledResolution` allocation at line 369 and an expanded-mode tick allocation at line 1204; impact is unmeasured. HUD uses an attribute/matrix stack guard, unlike chams' queried snapshot.

**Concrete scaling lead:** [ProfileUuidSet:1289](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/PlayerMinimapRenderer.java#L1289) stores primitive UUID halves in reused arrays. `add` calls linear `contains` for each UUID, and `countMissingFrom` performs another nested linear search. Rebuilding/churn-comparing loaded and marker sets therefore has quadratic growth in set size despite avoiding object allocation. This is diagnostic work, includes the disabled-minimap loaded census, and has no timing isolated from other marker-tick work. It is an attractive measurement seam, not proof of a material crowd bottleneck.

### Minimap world/chunk arrival and upload boundary

[MinimapTerrainManager.java:123](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L123) runs on client ticks, prepares the active cache, samples under a 500,000 ns deadline/768-sample ceiling, then flushes dirty textures. Only sampling is inside that deadline: preparation, texture creation, dirty-region discovery and GL uploads are outside it. A sample finishes before the next deadline check, so a costly column can overshoot; the 0.5 ms number is not a hard bound on total tick time.

Existing protections are substantial:

* Separate normal/expanded 256×256 ring caches, reusable validity/color/height/dirty/upload arrays and mutable block position ([storage:507](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L507)). Movement reuses overlap and queues exposed samples; world changes reset/reinitialize ([558](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L558), [583](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L583)). HUD draw at line 168 consumes textures; it does not sample chunks.
* Idle caps reduce from 768 to 256/128/64 after 20/80/200 stable ticks ([761](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L761)). Movement/pending/dirty/full-upload work demands full speed; changed samples reset stability in `finishTick`. BedWars expanded prewarm requires active-tick headroom and gets a smaller 125,000 ns/192-sample slice ([160](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L160), [253](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L253)). Its prepare/upload work also extends beyond the sampling deadline.
* A small chunk cache is scoped logically to each sample footprint (`footprintChunkCount=0` at [880](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L880)); [979](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L979) checks loaded chunks before direct lookup. Heightmap/direct section access replaces normal deep world scans, but empty near columns may use a top-section repair scan ([925](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L925), [960](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L960)). Biome-tinted blocks call `colorMultiplier`; no off-thread world snapshot is present.
* [Flush:1150](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L1150) does an initial/reset full upload, otherwise merges dirty rectangles and uses reusable scratch/`uploadTextureSub`; no per-tick rectangle/time cap appears in this flush. Initialization is a different path from ordinary steady updates.

**Arrival uncertainty:** unloaded placeholders remain revisitable, but this canonical source shows pending samples plus cyclic near/far refresh ([842](../../weave-mods/optimal-zone/src/main/java/com/atw/optimalzone/render/MinimapTerrainManager.java#L842)), not a chunk-packet listener, chunk-arrival dirty queue or unloaded-only priority queue. Arrival while idle is discovered when a maintenance sample revisits that pixel; discovering changes then restores full-speed maintenance. The README's quick-repair wording must not be treated as proof of packet-driven invalidation. Measure both frame/tick tails and time until newly loaded terrain appears before proposing scheduling/coalescing. No larger upload budget, background live-world reading or packet reordering is justified by existing profiles.

## Packet listeners and network/main queue

Canonical mod search found **one ATW packet listener**, [LevelHead Send:474](../../weave-mods/atw-levelhead/src/main/java/com/atw/levelhead/ATWLevelHead.java#L474). It rejects cancelled/non-chat/already-handled packets before reading command text. Slash commands synthesize `ChatEvent.Sent` synchronously and cancel if handled. [ChatPacketOrigin.java:10](../../weave-mods/atw-levelhead/src/main/java/com/atw/levelhead/hook/ChatPacketOrigin.java#L10) uses a synchronized weak packet map; the membership check is on outgoing chat, not all incoming gameplay packets. [Compatibility hook:19](../../weave-mods/atw-levelhead/src/main/java/com/atw/levelhead/hook/ChatCommandCompatibilityHook.java#L19) marks vanilla-created chat packets without reposting events. Overlay remains unsubscribed; do not introduce a second bridge or asynchronous command-cancellation race.

Local Weave 1.4.1 reference [PacketEventHook.kt:15](../../upgrade-work/ports/atw-rebrand/reference/weave/api/v1_8/src/main/kotlin/net/weavemc/api/hook/PacketEventHook.kt#L15) constructs/posts Send at `sendPacket` entry, and [line 36](../../upgrade-work/ports/atw-rebrand/reference/weave/api/v1_8/src/main/kotlin/net/weavemc/api/hook/PacketEventHook.kt#L36) constructs/posts Receive at `channelRead0` entry. [EventBus.kt:58](../../upgrade-work/ports/atw-rebrand/reference/weave/api/src/main/kotlin/net/weavemc/api/event/EventBus.kt#L58) dispatches synchronously on the caller, walks superclass listener lists, filters to a new list and invokes consumers. The existing reference API jar corroborates that filtered-list allocation; JIT elimination/effective allocation is unmeasured. Copy-on-write listener registration is not itself a per-packet copy. Canonical ATW render/tick subscriptions mostly use direct consumers; reflection consumers exist for annotation-based subscriptions in the API.

Built-in [CommandBus.kt:71](../../upgrade-work/ports/atw-rebrand/reference/weave/api/v1_8/src/main/kotlin/net/weavemc/api/command/CommandBus.kt#L71) also listens for tab-completion Send and [Receive:120](../../upgrade-work/ports/atw-rebrand/reference/weave/api/v1_8/src/main/kotlin/net/weavemc/api/command/CommandBus.kt#L120). Thus “one ATW listener” does not mean one total API listener. Receive dispatch at channel entry must not be assumed to be on the Minecraft main thread; EventBus adds no queue/handoff. Send executes in its caller's context, also not universally a Netty thread.

No canonical ATW gameplay-receive/chunk/metadata/scoreboard packet listener or packet batching/reordering layer was found. This is a bounded statement about inspected canonical mods, not every installed Lunar/third-party transformer. A hot stack, cache hit count or lowered allocation alone is not a promotion criterion. **Second window: stationary join/rejoin or chunk-arrival burst**, analyzed separately from settled crowd and terrain traversal.
